# R1 Adversarial QA and Hardening

Status: **IMPLEMENTED** for the R0/R1 delivery on source line `2.7.67`.

This is the mandatory second-pass review performed after the first implementation. It treats a green happy path as insufficient and attacks identity, lifecycle, resource bounds, idempotency, privacy and operator-confirmation seams. It does not claim that the later R2/R3 roadmap is complete.

## Findings and upgraded solution

| ID | Weakness found in first solution | Failure or performance risk | Upgrade applied | Regression evidence |
|---|---|---|---|---|
| QA-01 | Support preview rebuilt its inputs again during export with a new timestamp and pseudonym salt. | The operator could approve one manifest but save a different bundle; B5 snapshot/log collection and hashing ran twice. | Cache the exact immutable built bundle for 60 seconds behind an opaque `previewId`; export with that ID writes the same `manifestHash` once and consumes the preview. Expired/mismatched IDs fail closed. | `DesktopSupportReplay.test.js` compares preview and exported hashes and rejects reuse. |
| QA-02 | Support collection called the full diagnostic read before the builder enforced its 256 KiB entry limit. | Up to 20 multi-megabyte artifacts could block Electron's main process and allocate far beyond the final 1 MiB bundle budget. | Add metadata-only listing and skip diagnostic artifacts above 128 KiB before content read; record a manifest warning. | `DesktopSupportReplay.test.js` uses a 129 KiB artifact and verifies skip/warning. |
| QA-03 | Every Diagnostics list/read constructed a new repository and reparsed/resolved config paths synchronously. | Frequent renderer polling caused avoidable disk and realpath I/O. | Cache one repository per `DesktopController` lifecycle and invalidate it only across successful start/stop boundaries. | `DesktopDiagnosticsRepository.test.js` removes the fixture config after first access and proves the cached repository continues safely. |
| QA-04 | A resolved incident key remained permanently deduplicated, while storage-protection success reset the whole mode circuit. | A later independent incident with the same stable key could disappear; a business recovery could erase unrelated transient crash history. | Reopen resolved keys as new episodes, close active episodes on explicit reset, and let B5 storage success resolve only its business episode without touching circuit failures. | `ModeFaultPolicy.test.js` proves republish-after-resolution and preserved unrelated failure count. |
| QA-05 | B5 operator retry cached only by caller-provided idempotency key. | Reusing the same key with another generation/episode could return an earlier acceptance and obscure a stale request. Cache entries also had no time bound. | Bind each key to bot/generation/episode/incident fingerprint, reject conflict, expire after five minutes and cap at 64. | `B5CraftModeService.test.js` verifies exact duplicate identity and conflicting-payload rejection. |
| QA-06 | Fleet emergency-stop cached promises without payload identity or time expiry. | A key could be reused for another bot set, or old completed transactions could accumulate/stay authoritative indefinitely. | Bind key to the sorted bot set, retain exact in-flight dedupe, add five-minute settled TTL, bounded capacity and never evict an in-flight transaction. | `FleetControlService.test.js` verifies same-promise dedupe and bot-set conflict rejection. |
| QA-07 | Secret-store parsing/decryption had no file, entry-count or ciphertext-length budget; its temp name was process-wide. | A corrupt/local hostile file could synchronously allocate/decrypt excessive input, and concurrent writes could collide. | Fail closed above 256 KiB/256 entries/64 KiB ciphertext, inspect size before read/decrypt, use unique temp names and cleanup failed owned temp files. | `DesktopSecretStore.test.js` proves oversize rejection occurs with zero decrypt calls. |
| QA-08 | Support validation trusted `entryCount`; redaction/pseudonym traversal treated repeated references as cycles and a self-caused `Error` could recurse indefinitely. | Tampered manifests could retain a valid-looking count; legitimate repeated evidence was lost; pathological errors could overflow the stack. | Validate `entryCount === files.length`, use ancestry-scoped cycle tracking in both redactor and pseudonymizer, and bound self-referential errors. | `TraceSupportBundle.test.js` and `primitives.test.js` cover all three cases. |
| QA-09 | Fatal recovery set the same `quitting` ownership flag that the normal `before-quit` transaction owns. | Two shutdown paths could violate the single-owner invariant and hide ordering regressions. | Fatal drain owns only bounded cleanup followed by `app.exit`; only `before-quit` marks normal final-quit ownership. | `DesktopShutdownSequence.test.js` source invariant passes. |
| QA-10 | The new `npm run support:validate` command had no input and therefore printed usage with exit code 2. | A documented package gate was unusable in automation, and a later command in a shell sequence could hide its failure. | Make the package command run a deterministic in-memory validator self-check; preserve explicit file validation as `support:validate:file -- <bundle.json>`. | The standalone package command returns PASS/exit 0. |
| QA-11 | Local AI denied `.env` through the generic dot-directory branch before the specific secret/environment branch. | Access was safely denied, but the wrong operator contract/message made the security regression test fail and reduced diagnostic precision. | Classify any `.env*` path segment before the generic ignored-path rule while retaining the same fail-closed error code. | `ProjectWorkspace.test.js` passes without opening any environment file. |
| QA-12 | Desktop first-start captured `process.env` before the lazy `createApplication` import triggered dotenv loading. | Headless could authenticate while Desktop used the same source tree but had no bot password on its first backend start. | Replace module-load side effects with explicit `RuntimeEnvironment`; DEV resolves process → dotenv fill-missing → encrypted store before controller construction, and restart uses the same resolver. | `DesktopStartupEnvironment.test.js` plus `DesktopFirstStartConnection.test.js` prove first-start credential delivery and fake-client login. |
| QA-13 | Environment objects and injected resolver outputs remained mutable/unvalidated. | A caller could change credentials during startup or return an array/null and fail later at an unrelated layer. | Validate every environment boundary, copy and freeze the resolved snapshot, and reject environment replacement while backend lifecycle is active. | `RuntimeEnvironment.test.js` and `DesktopStartupEnvironment.test.js` cover invalid shapes, immutability and lifecycle guard. |
| QA-14 | Runtime parity diagnostics rehashed the complete config tree on every readiness request. | Repeated first-run/diagnostics refresh could create avoidable main-process disk and hashing pressure. | Add a bounded five-second cache, single in-flight sample and explicit force refresh while retaining read-only behavior. | `DesktopRuntimeProvenanceService.test.js` proves cache reuse and exact forced rescan count. |
| QA-15 | Parity scan checked file size before read but did not recheck the returned byte length. | A local file change between stat/read could bypass the declared scan budget and allocate/hash an oversized payload. | Recheck per-file and total byte budgets after read; reject unsafe root/symlink state and never return raw filesystem error text. | `DesktopRuntimeProvenanceService.test.js` mutates a file after stat and gets `DESKTOP_CONFIG_PROVENANCE_BYTE_LIMIT`. |
| QA-16 | Desktop runtime preparation had no idempotent/single-flight contract. | Duplicate bootstrap invocation could run two migrations and create divergent secret/provenance owners. | Cache the immutable prepared result and share one preparation promise; failed preparation clears only the in-flight owner for a safe retry. | `DesktopStartupEnvironment.test.js` calls prepare twice and proves migration/secret/environment order occurs once. |
| QA-17 | Fixing startup directly in `main.js`/`DesktopController` would grow already frozen compatibility façades. | A correct bug fix could silently worsen the architecture debt and make the next incident harder to isolate. | Physically extract runtime bootstrap, profile CRUD, mode config, fleet control and shared result contracts; lower the controller non-growth budget from 1128 to 986 lines. | Static-quality gate manages 91 files and rejects façade regrowth; Desktop controller/fleet/config tests remain green. |
| QA-18 | Local update ZIP excluded runtime/secrets/dependencies but did not explicitly exclude `.git`. | A full delivery could include repository history, deleted-content blobs and unnecessary private metadata despite passing the former release contract. | Add `.git` as a forbidden path segment shared by staging and post-build ZIP verification. | `ReleaseZipContract.test.js` rejects a `.git/objects/...` entry and the produced delivery is reverified after compression. |
| QA-19 | Update packaging depended on `Compress-Archive` module autoload. | A valid Windows host could have PowerShell available while `Microsoft.PowerShell.Archive` fails to load, blocking every delivery after all code gates pass. | Invoke the built-in .NET `System.IO.Compression.ZipFile.CreateFromDirectory` API from the bounded packager process; retain post-build ZIP contract and SHA-256 verification. | `UpdatePackageWriterContract.test.js` locks the writer path; the delivery command verifies the produced central directory. |
| QA-20 | Architecture baseline counted generated `out/` artifacts as repository inventory. | Creating a valid delivery made the next quality lane fail with stale file counts, encouraging accidental baseline capture of binaries. | Align baseline exclusions with release/build boundaries: `.git`, `.tmp`, `coverage`, `data`, `node_modules`, `out`, real env files and logs stay outside inventory/fingerprint. | `ArchitectureBaseline.test.js` covers every excluded class; packaging no longer changes baseline counts. |
| QA-21 | Release denylist was partly path-prefix based and case-sensitive. | On Windows, `.ENV.PRODUCTION`, `DATA/...`, an unexpected data subdirectory, a log outside known prefixes or `secrets.json` could enter a delivery. | Normalize policy paths case-insensitively and reject all `data` segments, real env variants, log files and secret-store filenames in both staging and post-build verification. | `ReleaseZipContract.test.js` covers mixed-case and unexpected-path variants; final ZIP verifier reports zero forbidden entries. |

## Remaining boundary

- The Electron E2E fixture needs `--no-sandbox` on this specific Windows host because the GPU/OS-crypt subprocess exits before renderer load without it. This flag exists only in the spawned test process. Production `BrowserWindow` remains configured with `sandbox: true`, `contextIsolation: true` and `nodeIntegration: false`.
- XP-403 is complete only for its R1 slice. Full XP-403 still depends on XP-205 and the R2/R3 capabilities named in the roadmap.
- MTTA/MTTR remain explicitly `NOT_MEASURABLE_YET`; R1 defines local metrics/privacy semantics but does not invent production telemetry history.
- Public Minecraft login, real encrypted operator secrets and AppData state remain a field acceptance boundary; offline fake-client evidence must not be relabeled as live-server proof.
